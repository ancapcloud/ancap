### 1.2. Возможный заработок и конверсия: сценарий, а не обещание

- Добавить локальный интерактивный расчёт ACP без API, кошелька и сохранения финансовых данных. Пять полей: цена, число предполагаемых заказов за период, комиссия в процентах, затраты на один заказ и фиксированные затраты за тот же период. Пользователь может изменить каждое допущение. Начальные значения `100 ACP, 10 заказов, 10%, 15 ACP/заказ, 50 ACP/период` — явно подписанный иллюстративный пример; `10%` не является заявлением о тарифе ANCAP или типичной доходности. Использовать арифметику с фиксированной точностью 8 десятичных знаков ACP, не создавать неточность расчётом денег через binary float.
- Формулы: `оборот = цена × предполагаемые заказы`; `комиссия = оборот × ставка / 100`; `сценарный остаток = оборот − комиссия − затраты на заказ × заказы − фиксированные затраты`. Показывать оборот, комиссию, затраты и остаток отдельно. Остаток может быть отрицательным; он не является выплатой, гарантированным доходом или прибылью после налогов.
- Если есть режим воронки, `предполагаемые заказы = обращения × предполагаемая конверсия / 100`; оба значения — явные допущения. Без подтверждённого источника не называть их фактическими метриками. Режим прямого ввода числа заказов допустим как минимальный срез.
- Пустые/некорректные значения не превращать в готовое обещание дохода. Проверять конечность чисел, неотрицательные входы, диапазон процентов 0–100; не показывать `NaN`/`Infinity`. Учитывать общую единицу времени. Пометка «Сценарий в ACP; продажи и выплаты не гарантированы» видна рядом с итогом на пяти языках.
- Не приравнивать ACP к EUR/USD, не вводить в этом калькуляторе обмен/вывод, не менять существующую доктрину ACP/wACP/sACP. Денежные затраты в иной валюте не складывать с ACP без отдельно обоснованного курса; текущий срез принимает только ACP-допущения.
- В блоке пользы объяснить: покупатель выбирает материал и критерии проверки; автор оценивает возможность заработка. Не обещать покупателю инвестиционную доходность, гарантированную экономию или заработок только от участия.

## Wave 1: foundation выполнен локально (2026-10-16)

Реализовано: модели/миграции `088_project_economy` + `089_economy_seed_owner`, API `/economy/*`, UI `/economy`, пять AI-демо как первые published platform seeds. При `FF_PROJECT_ECONOMY=false` видны только seeds; create/publish/apply закрыты. Community UGC (человек создаёт draft → publish → заявка) — следующий шаг после включения флага.

Рекомендуемый следующий срез community: **человек создаёт draft → публикует → другой пользователь видит проект и подаёт заявку на задачу → автор видит заявку**. Это каталог и подбор участников; принятие заявки не означает приёмку результата, оплату или заработок.

Перед реализацией согласовать следующие условия в каноническом документе:

- Существующие архитектурные правила: модели в `app/db/models.py`, Pydantic в `app/schemas/project_economy.py`, бизнес-логика в `app/services/project_economy.py`, router в `app/api/routers/project_economy.py`. Номер/родителя миграции определить по фактическому Alembic head.
- Базовый состав: Project, Task, Application. Offer добавлять только при ясной необходимости; до заказа и платежа это объявленная цена/ориентир бюджета, а не payment snapshot или «зарезервированные средства». ACP-суммы хранить через Decimal/Numeric согласно существующей точности, не float.
- Статус публикации (`draft/published/archived`) и характер проекта (`concept/demo/community project`) независимы. Published не означает проверенный результат или доступность физической услуги.
- Владелец и податель заявки определяются сервером из auth. Публично видны только published; собственные drafts/archived доступны владельцу. Редактирование задач и просмотр всех заявок — владельцу; участнику — собственная заявка. Чужие drafts не раскрывать.
- Полный API-контракт должен включать чтение проекта по slug для `/economy/[slug]`, «мои проекты», пагинацию, редактирование задач и явные переходы статусов. Не ограничиваться POST/GET списка, если UI требует detail/edit.
- Определить ограничения: уникальный slug, FK, timestamps, валидные статусы, неотрицательные суммы, ограничение размеров текста, защита от повторной заявки. Сохранять submitting user; agent_id при необходимости добавлять с проверкой полномочий.
- `FF_PROJECT_ECONOMY=false` по умолчанию: информационный preview доступен, операции создания/публикации/заявок закрыты сервером, публичные данные не раскрываются. Ошибка API в UI не маскируется успешным пустым каталогом.
- Сначала human-only. Запросы публикации от имени агента без проверенной делегации получают 403. Клиентский `permission=true` не является разрешением. Для следующего среза нужен сохранённый, созданный авторизованным владельцем, ограниченный по действию и отзывной grant с проверкой agent ownership. Проверить существующий путь регистрации агента: сейчас он допускает `body.owner_user_id` без authenticated user, поэтому поле ownership само по себе недостаточно как доказательство делегации.
- Если будет выбор исполнителя, сохранять его реальное состояние. Не делать fake/mock accept, не утверждать completion, payout, escrow или резервирование денег.
- Публичные отзывы/рейтинги проектов в первый каталог автоматически не включать. Сначала согласовать модель достоверного происхождения отзыва, право его публикации и модерацию. Публикация/отклик/выбор исполнителя ещё не подтверждают выполненную работу и не дают verified-completion badge.
- Переход к проектированию Wave 2 требует не только исправного каталога: измерить подбор по реальным задачам, принятие полезных цифровых результатов, повторный спрос и стоимость человеческой проверки. Предлагаемые стартовые ориентиры — 10–20 реальных задач, 5 внешних покупателей и 10 принятых результатов через уже разрешённый коммерческий путь; это цели пилота, не текущая статистика. Промо-ACP и внутренние тесты не подменяют покупателей.

### Обязательная изоляция будущих API-тестов

При подготовке задания обнаружено: `tests/conftest.py` без `TEST_DATABASE_URL` выбирает локальную БД `ancap`; при сбое Alembic в fixtures предусмотрен `DROP SCHEMA public CASCADE`. Поэтому формулировки «использовать тестовую БД» недостаточно.

До импорта pytest/conftest создать отдельную одноразовую PostgreSQL DB, установить `TEST_DATABASE_URL` и выполнить preflight: явный allowlist локального тестового инстанса, подтверждение только что созданного уникального имени БД, изолированная роль с доступом лишь к ней, отсутствие fallback на рабочую БД. Не печатать секреты. При провале preflight API-тесты не запускать; исправить локальное тестовое окружение.

Alembic migration проверить отдельно на одноразовой БД: её сбой должен быть видимым и не считаться успехом после `create_all`/stamp fallback. Лишь затем запускать `pytest tests/api/test_project_economy_smoke.py -q` с проверенной переменной окружения. Не применять миграции на production.

Будущая приёмка включает persistence после перезагрузки, чужой draft и чужое редактирование, agent без grant и чужой agent, flag off, дубликат заявки, отрицательную сумму и отсутствие любых ledger-эффектов. Это будущие проверки, в Wave 0 их не запускать и не отмечать выполненными.

## Wave 2: только отдельный явный запрос

Заказ, payment intent/credits, приёмка результата, idempotent ledger split, возвраты/споры и журнал событий проектируются отдельно после рабочего каталога. Сначала определить договорённости участников и получателей, затем интеграцию с текущим ledger. Проценты и реальные выплаты не придумывать. Мобильные экраны — после стабильного API и без смешивания с текущим WIP vault.

Связанный с принятой работой отзыв, подтверждённая атрибуция заработка и фактическая конверсия проектной воронки проектируются с этим контуром. Сценарный калькулятор не становится источником фактической аналитики. Допуск к масштабированию — измеренная экономика повторных заказов и проверенные отмены/возвраты/споры, а не заполненность витрины.
