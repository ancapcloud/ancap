# Research Operations: bounded agency pilot

Updated 2026-10-28. This is the delivery sequence for the active Research
Operations hypothesis, subordinate to monetary integrity and actual-cost P0s.
Reuse Studio projects, roles, workflows, review, subscriptions and repeats.

## Evidence and positioning

The operator supplied a strategy recommendation on 2026-10-28 (source text
SHA-256 `18a67eea7221527356fe292dbda7707714b887c0048ad7a36aa7110bed62f003`).
The document explicitly did not verify current competitor websites, prices,
reviews or ANCAP production behaviour. It is a product/market experiment,
not a completed market audit or evidence of paying demand.

Start with small agencies maintaining materials for several crypto clients.
Compare demand with a narrow control group of B2B communications agencies
serving technology clients; do not build a second product in parallel.
Sell a bounded client update, not generic access to agents. Company valuation,
token price/capitalization and ACP turnover are different measures.

- [ ] Conduct roughly 12 crypto-agency and 8 control-segment interviews;

- [ ] Offer a four-week paid pilot before expanding automation: two projects,
  up to ten agreed public URLs each, baseline claim map and four weekly updates,

- [ ] Test EUR 600 as a proposed price, not published willingness-to-pay or a
  new checkout SKU. Seller, taxes, PSP approval, refunds and payment provenance
  must be established before activating an external payment adapter.
- [ ] Measure onboarding, manual review and support; test one-hour onboarding,
  two-hour total review and EUR 60 external-consumption caps as proposed limits,
  not measured costs. Never hide unpaid founder work or silently lower quality.
- [ ] Observe use of at least three of four updates, resolve critical errors,
  record complete costs and seek an independent payment for the next period.
  Only count renewal when the renewal was due; record refusals and denominators.

No outreach, paid service purchase, real payment, model charge or customer email
is authorized by this roadmap alone.

## Implementation order and acceptance

### ROP-01 — sources, evidence links and draft packet

- [x] Project source register with permission-basis attestation, URL, status,
  check timestamp, text/raw hashes and bounded version history (migration 093).
- [x] On-demand public HTTPS GET: validate DNS and pin the selected public IP;
  preserve Host/SNI; no redirects, proxy environment, authentication or cookies.
  Only UTF-8 HTML on port 443, no query/fragment, 256 KiB response, 16,000 text
  characters and 12-second overall deadline. Reject unsupported content, do not
  silently truncate it and call the truncated body a complete source.
- [x] Baseline/unchanged/raw-HTML-only/text-change/unavailable states, bounded
  before/after text excerpts, full normalized snapshots on explicit request.
  Text change requires human review; materiality is not automatically inferred.
  Unavailable never becomes "no change"; last successful evidence is retained.
- [x] Manually reviewed claim → exact source-text hash and bounded matching
  excerpt. A changed hash requires re-review; unavailable sources cannot support
  a fresh claim. A citation is evidence from that source, not independent truth.
- [x] Studio project panel in EN/RU/UK/DE/zh-Hant; private JSON and readable-text
  draft exports include source metadata, claims, unresolved states and a hash.
  Source text is displayed as text, not HTML; no model/tool instructions are
  executed from a source.
- [x] Owner/editor writes, viewer reads, foreign project denial and private
  no-store responses; source/claim/version limits and check cooldown.
- [x] Sources expire using the project's retention setting at registration;
  checks do not extend that deadline. Expired content disappears from API reads;
  Studio worker cleanup deletes up to 100 expired sources per tick with cascading
  snapshots/claims. Project deletion cascades all research content.
- [ ] CI and deployed migration/UI/live-source acceptance on a fixed release.

This is a manual pilot foundation. Its draft packet is not an accepted release,
scheduled monitoring, delivery or a billable completed workflow. Existing paid
run counts, customer acceptance and revenue are not inflated by source checks.
There are no new LLM calls, wallet capabilities or payment/delivery side effects.
Permission attestation does not independently verify collection rights or source
accuracy. Operators select lawful sources and avoid secrets/personal data.

Limits: ten sources per project, twenty distinct raw snapshots per source,
fifty append-only claims per source, one check per source per sixty seconds.
When a version limit is reached, collection refuses; it does not claim freshness.
Changing project settings does not extend existing source retention. Dynamic
JavaScript, authenticated pages, PDFs, redirects and non-UTF-8 are not supported.
Raw HTML is hashed and discarded; normalized text is retained to the deadline.

### ROP-02 — one version-bound reviewed client release

- [ ] Persist an immutable packet containing source IDs/hashes, changed claims,
  proposed edits, unresolved questions and exact included workflow result hashes.
- [ ] Reuse Studio review/assessment; reject stale result/source versions,
  concurrent review conflicts and permission changes. Do not create a second
  disconnected approval system or mark a draft as an approved paid result.
- [ ] One operator-selected delivery adapter only after demand: durable outbox,
  unique release/destination key, explicit approved recipient and current rights.
  Repeated requests cannot create a second message. Ambiguous send outcomes stay
  unknown until provider evidence; do not claim exactly-once SMTP delivery.
- [ ] Cross-client isolation, version/revocation, interrupted send and replay
  tests; local/mock delivery tests before separately approved live acceptance.

### ROP-03 — bounded recurring collection and quality

- [ ] Reuse published Studio schedules after a paid pilot establishes source
  types/frequency. Bind source list, retention and quotas to a published version.
- [ ] Hard per-run/project request and retry quotas plus existing spend caps;
  no paid external calls after exhaustion, no indefinite retries or silent gaps.
- [ ] De-identified evaluation fixtures: price/product changes, markup noise,
  unavailable source, contradictions and malicious embedded instructions.
  Review errors and cost before changing model or prompt; do not train on client
  material or publicly export it without rights and consent.
- [ ] Test proposed useful-alert 70%, correct claim-link 90% and accepted-packet
  80% thresholds on agreed samples. These are pilot targets, not current metrics.

### ROP-04 — actual economics and renewal

- [ ] Complete provider/document reconciliation in the existing cost track;
  explicitly record unknown model/data/infra/review/support/fee expenses and
  avoid counting creator payout twice. Keep currencies separate.
- [ ] Durable external-payment / delivery / acceptance / manual-work / refund /
  renewal-due events with immutable timestamps, provenance and replay protection.
  Internal/test credits and top-ups are not external recurring revenue.
- [ ] Per-client period summary: delivered and accepted exact versions, revisions,
  manual work and evidenced costs; unknown economics remains unknown.
- [ ] Reuse subscriptions/repeats for an explicitly confirmed next period;
  measure due-renewal cohorts, expansion, concentration and refusal reasons.

### ROP-05 — repeatable onboarding and validated integrations

- [ ] Copy only reusable settings, source categories and packet templates,
  never previous client documents, credentials, identifiers or personal data.
- [ ] Validate a proposed 30% reduction in comparable onboarding effort before
  expanding template tooling. Add integrations only for observed paid processes.

## 90-day decision sequence

Days 1–14: interviews, existing paid-run/acceptance/repeat demonstration on a
fixed commit, manual baseline and ROP-01. Days 15–30: test two independent pilot
payments and one reviewed packet flow. Days 31–60: serve 3–5 pilots only if
demand exists; reduce factual errors and manual effort. Days 61–90: seek due
renewals, expansion and repeatable onboarding. These are experiments, not sales
forecasts or delivery promises. No exact company valuation is calculated here.

Stop or narrow if alerts are not useful, updates are too infrequent, customers
rebuild every packet, manual work erases contribution or pilots do not renew.
Do not respond by adding unrelated verticals, a new universal builder, a new
foundation model, unlimited integrations, token incentives or autonomous payment.
